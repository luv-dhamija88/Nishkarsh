# Nishkarsh | V0.1

## 1. Title

Nishkarsh v0.1 MVP Architecture for AI-Native Incident Intelligence


## 2. Context

Nishkarsh is a portfolio-grade AI-native incident intelligence platform focused on turning noisy operational logs into actionable conclusions for on-call and platform workflows.

The project must demonstrate real backend and distributed systems engineering depth, not just AI integration. The architecture needs to show practical event-driven design, operational observability, and production reliability thinking while remaining executable by one engineer.

Primary implementation constraints:

- Solo engineer building and operating the MVP.
- Monorepo-driven delivery for fast cross-service iteration.
- Vertical slices over broad horizontal platform work.
- Production-style architecture without enterprise-scale overhead.

## 3. Problem Statement

Production systems generate high-volume logs that are difficult to parse during incidents. Raw logs are noisy, repetitive, and low-signal under time pressure. Engineers need grouped incidents with concise summaries and probable causes, not unstructured event streams.

The system must reliably ingest logs, process them asynchronously, group related failures, and produce AI-assisted summaries without blocking ingestion or query paths.

## 4. Product Goals

- Ingest logs through OpenTelemetry-compatible pathways.
- Process logs asynchronously through Kafka.
- Group repeated failures into incidents.
- Generate AI summaries after incident grouping.
- Expose incident and summary data to a simple dashboard.
- Instrument all services with operational telemetry.
- Demonstrate production engineering fundamentals in an MVP scope.

## 5. MVP Scope

Included in v0.1:

- Log ingestion
- OTEL collector integration
- Kafka event pipeline
- Incident grouping
- AI-generated incident summaries
- Basic dashboard
- Production-style observability

## 6. Non-Goals

Out of scope for v0.1:

- Kubernetes
- Multi-region deployment
- RBAC and enterprise IAM
- Multi-tenancy
- Billing and metering
- SSO
- AI agents and autonomous remediation
- RAG and vector databases
- ClickHouse
- Fine-tuning and complex ML pipelines
- Service mesh
- Pulsar
- Enterprise security framework rollout

## 7. Architecture Overview

End-to-end flow:

Application Logs
-> OpenTelemetry Collector
-> ingestion-service (Java Spring Boot)
-> Kafka topic raw-logs
-> incident-processor (Java Spring Boot)
-> PostgreSQL incidents and grouped metadata
-> Kafka topic incident-created
-> ai-summary-worker (Python FastAPI)
-> OpenAI API
-> PostgreSQL incident_summaries
-> query-service (Java Spring Boot)
-> Next.js dashboard

Architecture principles in this flow:

- Decouple ingestion from processing to absorb spikes.
- Keep AI processing asynchronous and non-blocking.
- Persist source truth in PostgreSQL for deterministic reads.
- Use explicit contracts across service boundaries.

## 8. Service Responsibilities

ingestion-service:

- Accept OTEL log payloads via HTTP endpoint.
- Validate required fields and normalize shape.
- Enrich metadata such as ingestion timestamp and source.
- Publish normalized events to raw-logs topic.
- Emit ingest success and failure telemetry.

incident-processor:

- Consume raw-logs.
- Group events by service name, error signature, and time window.
- Classify severity based on frequency and error type heuristics.
- Persist grouped incidents to PostgreSQL.
- Publish incident-created events for new or materially updated incidents.

ai-summary-worker:

- Consume incident-created.
- Fetch grouped context from PostgreSQL.
- Build deterministic prompts with bounded context.
- Call OpenAI API with timeout and retries.
- Store summary, probable root cause, and action items.
- Publish incident-summarized event for downstream updates.

query-service:

- Serve dashboard APIs for incidents and summaries.
- Provide filtering by time and severity.
- Return counts and basic aggregate metrics.
- Keep read path isolated from write-heavy consumers.

dashboard:

- List incidents with status, severity, and timestamps.
- Show grouped occurrence counts and affected services.
- Display latest AI summaries and recommendations.

## 9. Event Flow

Flow sequence:

1. OTEL collector forwards logs to ingestion-service.
2. ingestion-service validates and emits raw-logs.
3. incident-processor consumes raw-logs and computes grouping keys.
4. incident-processor persists incident state and emits incident-created.
5. ai-summary-worker consumes incident-created and generates summary.
6. ai-summary-worker stores summary and emits incident-summarized.
7. query-service serves consolidated incident and summary views.

Ordering and delivery assumptions:

- Per-partition ordering is used for local event ordering.
- At-least-once delivery is expected across Kafka consumers.
- Idempotent processing is required in consumers and writes.

## 10. Data Flow

Write path:

- Logs arrive through OTEL into ingestion-service.
- Events travel through raw-logs.
- Incidents are materialized in PostgreSQL by incident-processor.
- Summaries are materialized in PostgreSQL by ai-summary-worker.

Read path:

- query-service reads incidents and summaries from PostgreSQL.
- dashboard calls query-service only; it does not read Kafka directly.

This separation keeps read latency stable while write pipelines operate asynchronously.

## 11. Kafka Design

Allowed topics in v0.1:

- raw-logs
- incident-created
- incident-summarized
- dead-letter

Topic intent:

- raw-logs: canonical normalized log events from ingestion-service.
- incident-created: grouped incident events for AI processing.
- incident-summarized: summary completion notifications.
- dead-letter: failed messages after retry exhaustion.

Partitioning strategy:

- raw-logs keyed by service name to preserve local service ordering.
- incident-created keyed by incident id for deterministic summary processing.
- dead-letter keyed by original topic plus key for triage.

Schema guidance:

- Keep event payloads explicit and versioned.
- Include event id, occurred_at, source_service, and schema version.
- Reject unknown mandatory-field omissions early.

Topic throughput observability:

- Track per-topic ingress rate (messages received by topic per second).
- Track per-topic egress rate (messages consumed and successfully processed per second).
- Track service processing ratio as egress divided by ingress over time windows to detect slowdowns.
- Alert when sustained egress is lower than ingress and consumer lag is increasing.

## 12. Database Design

Minimal PostgreSQL tables for MVP:

- logs
- incidents
- incident_summaries

Logical model:

- logs stores normalized raw records and linkage metadata.
- incidents stores grouped incident state with severity and counters.
- incident_summaries stores AI outputs tied to incident id and model metadata.

Data constraints:

- Stable incident identifier for idempotent writes.
- Unique index on incident_summaries.incident_id for latest-summary overwrite semantics in MVP.
- Timestamps on all records for ordering and operational analysis.

## 13. AI Processing Design

AI processing is downstream of incident grouping by design.

Reasoning:

- Summarizing individual logs is noisy and expensive.
- Grouping first produces higher-signal, lower-volume AI calls.
- Cost and latency become tractable for a solo-operated MVP.

Prompt strategy:

- Include service context, grouped error signature, frequency, and representative samples.
- Limit token usage by capped sample size and deterministic truncation.
- Request structured output: summary, probable root cause, severity hint, action items.

Operational controls:

- Timeout and bounded retries for provider calls.
- Persist provider error metadata for failed attempts.
- Do not block ingestion or incident materialization on AI failure.

## 14. Observability Design

All services are instrumented with OpenTelemetry.

Metrics to capture:

- Request latency
- Kafka publish latency
- Kafka topic ingress rate
- Kafka topic egress rate
- Service processing ratio (egress/ingress)
- Kafka consumer lag
- AI response latency
- Token usage
- Summary failures
- Retry counts
- DB query latency

Telemetry stack:

- OTEL SDK in services
- OTEL Collector for export pipeline
- Prometheus for metrics storage
- Grafana for dashboards and alert visualization

Minimum dashboards:

- Ingestion throughput and error rate
- Consumer lag by topic and group
- Topic ingress versus egress trend by service and topic
- Processing ratio by service (ingestion-service, incident-processor, ai-summary-worker)
- AI call latency and failure rate
- Incident creation rate and summary completion lag

## 15. Failure Handling Strategy

Principles:

- Fail explicitly with observable error signals.
- Isolate failures by stage to avoid cascading outages.
- Prefer partial availability over global pipeline blocking.

Service behavior:

- ingestion-service returns validation errors for malformed payloads and records counters.
- incident-processor skips poison messages to dead-letter after retries.
- ai-summary-worker records failed summary attempts and allows incident visibility without summary.
- query-service always returns incident records even when summary is missing.

## 16. Retry + DLQ Strategy

Retry model:

- Consumer-level bounded retries with exponential backoff.
- Retry counts stored in message headers where supported.
- Max attempts configured per service with conservative defaults.

DLQ policy:

- After max retry exhaustion, publish to dead-letter topic.
- Include original topic, partition, offset, key, error class, and timestamp.
- Surface dead-letter volume in Grafana and include runbook for replay.

Idempotency expectations:

- incident-processor upserts incidents by grouping key and time window.
- ai-summary-worker upserts summaries by incident id.

## 17. Security Considerations

MVP-level security posture:

- Store secrets via environment variables only.
- Do not commit API keys or credentials.
- Restrict exposed service ports in Docker Compose.
- Validate and sanitize incoming payload fields.
- Redact sensitive fields before sending prompt context to AI provider when feasible.

Not in v0.1:

- Enterprise IAM and centralized secret manager rollout.
- Full PII governance framework.

## 18. Scalability Expectations

Expected MVP scale:

- Low to moderate event volume suitable for a single Kafka broker and single PostgreSQL instance.
- Horizontal service scaling possible later via stateless service replicas.

Current practical target:

- Demonstrate architecture correctness, backpressure handling, and observability under load bursts, not internet-scale throughput.

## 19. Known Limitations

- Single-region local-first deployment model.
- Kafka and PostgreSQL are single-instance in Docker Compose.
- Incident grouping heuristics are rule-based and limited.
- AI summary quality depends on prompt quality and provider behavior.
- No automated replay tooling beyond manual DLQ procedures in MVP.

## 20. Tradeoffs

Monorepo:

- Pros: simpler cross-service changes, lower coordination overhead.
- Cons: repo noise and potential CI growth.

Java for backend services:

- Pros: mature concurrency model, strong Kafka and Spring ecosystem.
- Cons: more boilerplate than dynamic languages.

Python for AI worker:

- Pros: rapid AI SDK integration and prompt iteration.
- Cons: polyglot operational overhead.

Kafka for async pipelines:

- Pros: durable decoupling and backpressure tolerance.
- Cons: operational complexity relative to simple queues.

PostgreSQL for MVP:

- Pros: reliable relational core, easy local operation.
- Cons: not optimized for very high-volume log analytics.

OpenTelemetry in MVP:

- Pros: production-grade instrumentation from day one.
- Cons: additional setup effort early.

Docker Compose over Kubernetes:

- Pros: faster local setup and lower cognitive overhead.
- Cons: less production orchestration realism.

Modular architecture over service explosion:

- Pros: clear boundaries without fragmentation.
- Cons: fewer independent deployment levers initially.

Async AI processing:

- Pros: protects ingestion and incident pipeline latency.
- Cons: summary eventual consistency.

AI after grouping:

- Pros: better signal, lower cost, improved relevance.
- Cons: added delay before summary availability.

## 21. Rejected Alternatives

- Synchronous AI summarization in ingest path: rejected due to latency coupling and failure propagation risk.
- Per-log AI summarization: rejected due to cost, noise, and weak operational value.
- Kubernetes-first deployment: rejected for MVP complexity overhead.
- Multi-repo setup at v0.1: rejected due to solo engineer coordination burden.
- ClickHouse-first data path: rejected as premature for MVP scale.
- Advanced ML training pipeline in v0.1: rejected due to scope and limited ROI for architecture demo.

## 22. Future Evolution Path

Post-v0.1 evolution gates:

- Add partition and consumer scaling based on observed lag.
- Introduce stronger incident lifecycle states and dedup logic.
- Add summary versioning and quality evaluation metrics.
- Add managed deployment options after local architecture stabilizes.

Any future change must be justified by measured bottlenecks or clear ownership boundaries.

## 23. Deployment Model

Deployment for v0.1:

- Docker Compose for all services and dependencies.
- Single local environment with deterministic startup order.
- Environment-based configuration for service endpoints and secrets.

Rationale:

- Maximizes implementation velocity.
- Keeps operational setup transparent for portfolio reviewers.

## 24. Local Development Strategy

- Use monorepo root as single workspace.
- Run infrastructure dependencies through Compose.
- Run each application service with local reload mode where practical.
- Validate contracts in packages/contracts before cross-service changes.
- Use seeded fixtures for repeatable integration tests.

Minimum development checks:

- API validation tests
- Kafka consumer and producer integration tests
- Incident grouping unit tests
- AI worker failure-path tests
- Query API contract tests

## 26. Engineering Principles

- Avoid overengineering.
- Keep MVP vertically integrated.
- Build working slices first.
- Preserve architecture clarity over abstraction density.
- Prioritize observability and operational correctness.
- Prefer explicit failure handling over silent degradation.
- Treat AI as an augmentation layer, not the system core.
- Focus on distributed systems reliability as primary complexity.

## 27. Risks

- Incomplete observability could mask pipeline bottlenecks.
- Weak idempotency could cause duplicate incidents or summaries.
- Poor grouping heuristics could reduce summary quality.
- AI provider latency spikes could increase summary lag.
- Solo-maintainer context overload could slow integration quality.

Mitigations:

- Baseline dashboards before feature expansion.
- Enforce deterministic keys and upsert semantics.
- Add test fixtures for grouping edge cases.
- Track AI latency and timeout percentiles.
- Keep ADRs and runbooks updated alongside implementation.

## 29. Conclusion

This ADR defines a realistic v0.1 architecture for Nishkarsh that emphasizes distributed systems correctness, asynchronous processing, observability, and practical AI integration while remaining executable by a solo engineer.

The MVP intentionally limits scope to the smallest production-credible slice: ingest, group, summarize, query, and observe. The architecture is modular, measurable, and implementation-ready without introducing unnecessary enterprise complexity.
